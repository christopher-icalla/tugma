How it works

From regulation to proof, in one traceable chain.

  1. Regulation → controlBSP and AMLC requirements map to deterministic, testable controls.
  2. Automated testsEvery transaction is tested; each failure records expected, actual, variance and tolerance.
  3. Exception workflowReview, remediation and evidence, verified by someone other than the resolver.
  4. Evidence packageA canonical manifest for the period, hashed with SHA-256. Same inputs, same hash.
  5. Stellar attestationOne wallet attests the hash on a Soroban contract; a different wallet countersigns.
  6. Independent verificationAnyone re-hashes the package and checks it on Stellar with open-source code.

Verify it yourself

No need to trust TUGMA.

Download a finalized package from the app, then check it with the open-source verifier. It rebuilds the canonical form, recalculates the SHA-256 and reads the attestation directly from the Stellar Testnet contract through Soroban RPC. The file never leaves your browser.

  • VALID the file is byte-for-byte the attested package
  • TAMPERED the contents changed after export
  • NOT ATTESTED no attestation matches the recomputed hash
cd verifier && corepack enable && pnpm install --frozen-lockfile
node bin/tugma-verify.js tugma-pkg-2026-01-01-2026-03-31.json

A valid result establishes package integrity, not that the contents are true or that the organization is compliant.

Stellar integration

An integrity layer, not a data store.

Wallet-signedUsers sign with Freighter. The API never holds a secret key and checks every signed envelope.
Data stays off-chainOnly a SHA-256 and an opaque organization id are public. What goes on-chain
